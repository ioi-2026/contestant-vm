Grading Environment

Grading System

The contest will use CMS (Contest Management System) as the grading system.

Grading is performed in a Linux environment configured by the Technical Committee. Contestant machines are intended to provide a similar local development environment, but an identical execution environment between contestant and grading workstations is not guaranteed.

Submitted C++ source files are compiled using GCC 13.3 or newer, matching the compiler family installed on contestant machines.

Recent GCC versions may consume excessive resources when compiling code that allocates dynamic data structures with a large constant size. This may cause compilation to exceed resource limits and fail.

The exact commands used for compilation will be shown on the grading system. With the exception of certain task types, the compilation command will generally be of the following format:

/usr/bin/g++ -DEVAL -std=gnu++20 -O2 -pipe -static -s -o task grader.cpp task.cpp

The compilation scripts provided to contestants use a similar compilation command, except that they do not include -DEVAL and use -g instead of -s.

Protocol Violation

A contestant may receive a Protocol Violation feedback if their program does not follow the correct protocol described in the problem statement. This typically happens in the following situations:

  • Reading from standard input or printing to standard output.
  • Calling exit().

Other violations of the protocol, particularly those involving grader procedure calls, should generally result in the solution being judged as incorrect. CMS may report these as:

  • Output isn't correct: Invalid argument - a grader procedure was called with invalid arguments.
  • Output isn't correct: Too many calls - a grader procedure was called too many times.

Output-Only Subtasks

If a task includes output-only subtasks, a single submission may contain:

  • At most one C++ source file.
  • Any number of output files, with at most one file per output-only subtask.

Submissions are evaluated according to the following rules:

  • For each programming subtask, the C++ source file, if provided, will be compiled and graded. If no source file is included, the score for that subtask will be 0.
  • For each output-only subtask, an included output file specific to that subtask will be graded. Otherwise, if a C++ source file is present, the compiled program will be executed and its output will be graded for that subtask.

Program execution is subject to the time and memory limits given in the grading system, regardless of the subtask type.

Task Attachments

There is an attachment package that you can download from the contest system, containing:

  • Sample graders.
  • Sample implementations.
  • Example test cases.
  • Compile, run, and submit scripts.

Each task has a subtask with index 0 which is worth 0 points. Unless specified otherwise in the problem statement, the test cases for this subtask are the same as the sample test cases included in the task statement and in the downloadable attachment.

When you test your code locally, use the scripts from the attachment packages. The compiler option is -std=gnu++20.

Sample Graders

Sample graders provide a basic mechanism for running your solution. In many cases they are simpler than the graders used to judge your solution.

When testing a program with the sample grader, your input should match the format and constraints from the task statement, otherwise unspecified behavior may occur.

If a sample grader procedure call violates constraints in the task statement, the sample grader may print an error message and terminate immediately. Unless specified otherwise, the error message is one of the following:

  • Invalid argument - a grader procedure was called with arguments which violate a constraint.
  • Too many calls - a grader procedure was called more times than the limit provided in the task statement.

Contestants can inspect the sample grader source code to see what triggers these errors and may modify the sample grader to print more information.

Alternative Submission Mechanism

In addition to submitting solutions through the CMS web interface, contestants may also use the submit script included in the task attachment package.

  • For tasks requiring a single source file, run the script with one argument: the source file to submit.
  • For tasks that allow or require one or more output files, run the script with all files the contestant wants to submit.

The script first attempts to submit the files online via CMS. If the submission is successful, it will appear in the CMS interface with feedback. If it fails, the submission is recorded offline on the contestant's machine.

When the contest is over, the scientific committee collects all locally recorded submissions and imports them into CMS in chronological order.
